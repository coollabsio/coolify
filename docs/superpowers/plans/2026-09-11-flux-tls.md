# Flux TLS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every production Sentinel-to-Flux connection use a Coolify-managed private CA, while supporting DNS, IPv4, IPv6, local development, renewal, rotation, and SSH recovery.

**Architecture:** Coolify owns a versioned installation CA and Flux leaf certificates. Flux loads a leaf from mounted files and fails closed outside explicit development plaintext mode. Coolify installs a versioned CA bundle on each host over SSH; Sentinel loads that bundle and tonic/rustls verifies both the chain and the URL identity.

**Tech Stack:** Laravel 12, Eloquent encrypted casts, PHP OpenSSL, Livewire 3, Pest 4, Rust 1.97, tonic 0.14.6, rustls, Docker Compose.

## Global Constraints

- The installation CA validity is 100 years.
- Flux leaf validity is 90 days and renewal starts at 30 days remaining.
- Use the private CA for DNS, IPv4, IPv6, self-hosted, cloud, and HTTP dashboard installations.
- Keep `PUSH_ENDPOINT` and `TOKEN`; do not add duplicate control-plane URL or token variables.
- SSH is the bootstrap and recovery channel.
- Production plaintext is rejected. Explicit plaintext is development-only.
- Keep all UI and behavior behind `SENTINEL_HOST_ENABLED` until rollout approval.
- Existing v4 Sentinel containers are unchanged.
